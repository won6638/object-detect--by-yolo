# YOLO-VLM Vision Pipeline

A modular real-time vision pipeline combining **YOLOE**, **BoT-SORT tracking**, user-selected object capture, and **local VLM inference with Qwen2.5-VL**.

The system detects and tracks objects from a live camera feed, allows the user to select detected objects or manually define regions of interest, captures the selected visual information, and sends it asynchronously to a local Vision-Language Model for identification.

The project was originally developed as the vision/backend component of an XR AI prototype and is being extended toward a modular vision system that can later support different cameras, VLM backends, XR interfaces, and motion hardware.

---

## Overview

The pipeline separates real-time vision processing from VLM inference.

```text
Camera
  ↓
YOLOE Detection / Segmentation
  ↓
BoT-SORT Tracking
  ↓
Object Selection / Manual ROI
  ↓
Image + Metadata Capture
  ↓
VLM Request Queue
  ↓
Local Qwen2.5-VL via llama.cpp
  ↓
Schema Validation / Evidence Validation
  ↓
Desktop HUD
```

The vision loop does not wait for the VLM response.

Detection, tracking, rendering, and VLM inference run across separate processing boundaries so that slow VLM inference does not block the camera pipeline.

## Key Features

- Real-time camera input
- YOLOE-based object detection and segmentation
- BoT-SORT object tracking
- Click-based object selection
- Manual ROI selection using mouse drag
- Persistent application-level object identities
- Automatic image and metadata capture
- JSON-based request and result records
- Asynchronous VLM processing
- Local Qwen2.5-VL inference through llama.cpp
- Structured JSON VLM responses
- JSON Schema validation
- Deterministic evidence validation
- Stale-response protection using request IDs
- SHA-256-based exact-image VLM cache
- Desktop OpenCV HUD
- Modular VLM and UI boundaries for future expansion

## Architecture

The integrated launcher runs multiple independent processes.

```text
run_integrated.py
│
├── llama-server.exe
│
├── VLM Harness
│   └── Qwen2.5-VL Provider
│
└── Vision Process
    ├── Camera
    ├── YOLOE
    ├── BoT-SORT
    ├── Selection
    ├── Capture
    └── OpenCV HUD
```

Communication between the vision process and VLM harness currently uses file-based IPC.

```text
capture/
├── queue.jsonl
├── events.jsonl
└── ...
    ├── original.jpg
    ├── llm.jpg
    └── record.json
```

`record.json` acts as the primary contract connecting object identity, capture metadata, detector information, VLM requests, VLM responses, validation results, and latency information.

For a more detailed explanation, see:

- [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)
- [`docs/EXTENDING.md`](docs/EXTENDING.md)

## Object Identity

The project distinguishes tracker identities from application identities.

### `track_id`

Runtime identity generated by the tracker.

A `track_id` may change due to tracker fragmentation or after restarting the program.

### `object_id`

Persistent application-level identity assigned to a user-selected object.

```text
object_id
 ├── capture_id
 │    └── request_id
 │
 └── capture_id
      └── request_id
```

This separation prevents asynchronous VLM responses from being displayed on the wrong object.

## VLM Pipeline

The VLM subsystem currently uses:

```text
Vision Process
    ↓
queue.jsonl
    ↓
VLM Harness
    ↓
LlamaCppProvider
    ↓
llama.cpp
    ↓
Qwen2.5-VL
    ↓
JSON Schema Validator
    ↓
Deterministic Evidence Validator
    ↓
record.json
    ↓
HUD
```

YOLO semantic labels are treated only as hints and are **not considered ground truth**.

The VLM is expected to independently inspect the captured image.

Detailed identity fields such as brand, product name, and exact model require stronger visual evidence than general object classification.

## User Controls

| Input | Action |
|---|---|
| Left click | Select a detected object and request identification |
| Mouse drag | Create a manual ROI and request identification |
| `C` | Re-identify currently selected objects |

## Requirements

The current implementation is primarily developed and tested on Windows.

Main software components include:

- Python
- PyTorch
- Ultralytics
- OpenCV
- NumPy
- llama.cpp
- Qwen2.5-VL

CUDA acceleration is automatically used when a compatible CUDA-enabled PyTorch environment is available.

Without CUDA, the vision process falls back to CPU inference.

## Local VLM

The default integrated configuration uses a local `llama.cpp` server.

Example configuration:

```json
{
  "local_vlm_server": {
    "enabled": true,
    "exe": "C:\\llama.cpp\\llama-server.exe",
    "repo": "ggml-org/Qwen2.5-VL-3B-Instruct-GGUF",
    "alias": "qwen2.5-vl-3b",
    "host": "127.0.0.1",
    "port": 8080,
    "gpu_layers": 99,
    "context": 4096
  }
}
```

Update `integrated_config.json` to match the local llama.cpp installation path.

## Running the Integrated Pipeline

On Windows:

```bat
run_integrated.bat
```

or:

```bash
python run_integrated.py
```

The launcher performs the following sequence:

```text
1. Preflight checks
2. Start or reuse the local llama.cpp server
3. Start the VLM Harness worker
4. Start the camera / YOLOE / HUD process
5. Monitor the processes
6. Shut down child processes when the vision UI exits
```

The launcher attempts to use:

```text
.venv\Scripts\python.exe
```

when a project virtual environment exists.

completed

unknown

## Async Safety

A core design rule of this project is:

> A VLM result must only be displayed if it belongs to the current request for the object currently shown to the user.

Each result card tracks:

```text
object_id
capture_id
request_id
```

If an old request finishes after a newer request has already been submitted, the stale result is not attached to the current object state.

Raw VLM output is also not shown directly to the user before validation.

## Current Limitations

The current version is still a prototype.

Notable limitations include:

- Desktop OpenCV UI
- File-based IPC
- Single local VLM provider implementation
- Manual ROI regions are currently not tracked
- Camera input is currently webcam-oriented
- Hardware motion control is not yet implemented
- VR/XR rendering is not yet integrated into the current version

Vision
VLM
UI
Transport
Hardware Motion

This repository contains the vision/backend work and subsequent extensions.
